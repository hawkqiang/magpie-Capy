# Capy 工具调度：<CMD> 协议 + Machine RPC 捕获（方案 B 现实评估）

## 已落地（HEAD，97 项测试全绿）

1. **`<CMD>` 标签协议**（替代 JSON 包）：模型输出 `<CMD>命令原文</CMD>`，命令体不经 JSON 字符串，`$`、引号、换行原样保留。插件解析后包成标准 `tool_calls`。这修掉了你遇到的 `$` 被吞、JSON 残缺问题。glm 3/3、deepseek 2/3 成功（对比纯 JSON 时的接近 0）。
2. **Machine RPC 捕获**（方案 B）：隧道收到 Capy 内部发起的 bash 调用时，记下 `{handler, params}`；模型没给 `<CMD>` 但内部发过命令时，把命令转成 DSH 调用（优先 `pwsh`）。命令意图来自模型，插件只翻译。
3. **基础设施过滤**：Capy 在每台机器注入 `__capy_co_author` / `.capy/guard` 等 git shim 脚本会走 bash handler，必须过滤，否则会执行垃圾。
4. **剥壳**：`pwsh -Command "..."` / `bash -c '...'` 外壳剥掉，避免嵌套调用。

## 真机测出的硬限制（重要，别当可修复 bug）

- **方案 B 捕获率低**：实测真任务命令约 1/4 被捕获；大量 bash 调用被 Capy 的 guard shim 占用。方案 B 是"额外机会"，不是可靠主路径。
- **`<CMD>` 遵守率概率性**：deepseek 常无视指令、直接回"执行通道已关闭"的文本；glm 更好但不稳定。这是提示词模拟工具的固有上限。
- **没有多轮重试**：DSH 只在传输错误时重试；模型返回 `stop`+文本被视为正常完成，不会自动再试。

## 结论

Capy 无原生 tools 通道，"伪装"到 100% 可靠做不到。当前实现（`<CMD>` + 方案 B 兜底）能把成功率从接近 0 提到 **1/4 ~ 全中**，但不保证。

**要稳定多轮调度，唯一可靠方案是换原生支持 tools 的模型**（gpt-6.2-astra / 官方 DeepSeek）。Capy 适合纯文本任务。

## 做过的错误判断（留作记录）

- 最早判断"历史污染"——被单次样本误导；新会话首轮就失败推翻。
- 再判断"工具数量阈值"——也被推翻，实际是概率性。
- 方案 B 初测"成功"实为转交了 guard 脚本垃圾，加过滤后暴露真实捕获率低。
