# 会话"不能调度"诊断（session-adc8f8b9 / session-349b9f63）

## 结论：Capy 方案 C 的工具调用是概率性的，不稳定——这是协议固有限制，不是可修 bug

两个会话都复现了"调度不动"。逐层排查后确认：

- 不是 Magpie 插件 bug：`tools` 确实下发了（38 个，含 `pwsh`/`read`/`write`），OpenAI `tool_calls` 出口也验证可用。
- 不是历史污染：全新会话（349b9f63）首轮就失败。
- 不是工具数量/长度阈值：1/24/38 个工具都分别成功过。
- 不是 system message：带/不带 7420 字符的真实 system 都分别成功过、也失败过。

**决定性证据（同一请求重复测试，结果随机）：**

| 测试 | 结果 |
|---|---|
| 1 个工具 ×5 次 | 5/5 返回 tool_calls |
| 38 个工具（短 user） | 返回 tool_calls |
| 38 个工具 + 一句 system | stop，0 调用 |
| 38 个工具（无 system） | stop，0 调用 |
| 38 个工具 + 真实 7420 字 system | 返回 tool_calls |

同样的工具集、同样的提示，结果在"正确返回调用"和"返回一段解释为什么不调用的文字"之间随机摆动。这是**提示词模拟工具（方案 C）的固有上限**：Capy 没有原生 tools 通道，模型只是被提示词"请求"输出 JSON 调用包，没有协议级强制，遵守与否是概率的。一旦它在文本里写了"没有工具可用"，用户再贴回去，就会自我强化。

## 修复

插件侧**无法修复**这个概率性。可选：

1. **需要稳定调度的任务，换原生支持 tools 的模型**（`gpt-6.2-astra` / 官方 DeepSeek）。这是唯一可靠方案。
2. Capy 只用于纯文本任务（不调度工具）。
3. 若必须在 Capy 上调度：首轮明确"只输出 tool_calls JSON"，失败就重试（这是概率游戏，不能保证）。失败时不要模型解释文字，直接丢弃重发。
4. DSH 侧若能在"模型返回 stop 且声明要调工具"时自动重试，可缓解，但改 DSH 超出本插件范围。

## 边界

不要把"调度不动"当作可修的插件 bug。它是 Capy 无原生 tools 通道 + 方案 C 提示词模拟的必然结果。真机数据表明成功率不稳定，不能作为生产调度路径。
